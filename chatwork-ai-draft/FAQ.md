# FAQ（よくある質問）

## Q1. config.js にエンドポイントURLを直書きして大丈夫？社内配布だから安全？

### 短い回答

**「社内配布だから安全」とは言えません。** ただし、正しく多層防御すればリスクは十分低くできます。

### なぜ「社内配布 = 安全」ではないのか

Chrome拡張のソースコードは**誰でも閲覧可能**です。

```
chrome://extensions → 拡張ID → ソースを表示 → config.js が丸見え
```

つまり社員であれば全員がURLとAPIキーを読めます。さらに以下のリスクがあります。

| リスク | 説明 |
|---|---|
| **退職者リスク** | 退職した社員がURLを知ったまま離職する |
| **端末紛失・盗難** | PCが盗まれればソースを閲覧される |
| **スクリーンショット** | DevToolsを開いた画面の共有で漏洩 |
| **マルウェア** | PC上のマルウェアが拡張ファイルを読み取る |
| **社内の悪意あるユーザー** | URLを知れば外部ツールからリクエスト可能 |

### ではどうすれば安全か？（多層防御）

**URLが漏れても被害を最小化する設計**が重要です。

#### 必須対策（これだけは必ずやる）

| # | 対策 | 効果 |
|---|---|---|
| 1 | **API Gateway でAPIキー認証を設定** | URLだけでは叩けなくなる（実装済み） |
| 2 | **APIキーにリファラー制限を設定** | Chatworkドメイン以外からのアクセスを拒否 |
| 3 | **HTTPS必須** | 通信内容の盗聴を防止 |

#### 推奨対策（100人規模なら検討すべき）

| # | 対策 | 効果 |
|---|---|---|
| 4 | **IP制限** | 社内ネットワーク以外からのアクセスをブロック |
| 5 | **レートリミット** | 不正な大量リクエストを防止 |
| 6 | **APIキーのローテーション** | 定期的にキーを変更し、漏洩の影響を限定 |
| 7 | **Cloud Audit Logs で監視** | 異常なリクエストパターンを検知 |

#### 理想的な構成（余裕があれば）

| # | 対策 | 効果 |
|---|---|---|
| 8 | **ユーザー認証（OAuth2 / IAP）** | 誰がリクエストしたか特定できる |
| 9 | **Chrome管理コンソールで配布** | インストール管理、自動更新が可能 |

### 現在の拡張の保護レイヤー

```
[社員のブラウザ]
    │
    │ ① APIキー認証（x-api-key ヘッダー）
    │ ② HTTPS通信
    │
    ▼
[GCP API Gateway]  ← ③ リファラー制限
    │               ← ④ IP制限（推奨）
    │               ← ⑤ レートリミット（推奨）
    ▼
[Application Integration]
    │
    ▼
[Gemini Flash API]  ← APIキーはGCP側のみで管理（拡張には非保持）
```

### 結論

- config.js にURLを書くこと自体は**実用上は許容範囲**
- ただし**URLだけでアクセスできる状態はNG**
- **APIキー認証 + リファラー制限/IP制限**の組み合わせが最低ライン
- 「URLが漏れた前提」で被害が起きない設計にすることが本質

## Q2. APIキーもconfig.jsに書いたら同じでは？

### 短い回答

**その通り、config.js のAPIキーも社員には見えます。** しかしそれでも意味があります。

### なぜそれでも認証が有効なのか

| 保護対象 | URL直書きのみ | URL + APIキー |
|---|---|---|
| 社外からの不正アクセス | URLが漏れたらアウト | URL+APIキー両方が漏れないと攻撃不可 |
| 退職者 | URLだけで叩ける | **APIキーをローテーションすれば無効化** |
| URLのクローラー発見 | そのままアクセス可能 | 認証で弾かれる |
| ログ監視 | リクエスト元の区別が困難 | APIキーで正規リクエストか判別可能 |

**最大のメリットはAPIキーのローテーション（定期変更）です。**
URLは構造的に変えにくいですが、APIキーは簡単に変更でき、
config.js を更新して再配布すれば全社員に一括反映できます。

### さらに強固にするには

個人別APIキーを設定画面で入力させる運用も可能です。

```
config.js の DEFAULT_API_KEY = '';  （空にする）
↓
各社員が設定画面で自分のAPIキーを入力
↓
API Gateway側で個人別キーを検証
```

これにより「誰がリクエストしたか」を特定でき、
退職時にその人のキーだけ無効化できます。

## Q3. Gemini APIキーが拡張に入っていないのはなぜ？

Chrome拡張のソースコードは `chrome://extensions` から**誰でも閲覧可能**です。
APIキーを埋め込むと以下の問題が発生します。

- APIキーが漏洩し、不正利用される
- 利用量の制御ができなくなる（高額請求リスク）
- キーのローテーションに全社員の再設定が必要

**対策**: Gemini APIキーはGCPサーバー側（環境変数 / Secret Manager）でのみ管理する。
拡張機能が持つのは API Gateway 用の制限付きキーのみで、Gemini APIキーには一切触れない。

## Q4. 社員のChatwork会話内容がAIに送られるのが心配

### 送信するデータ

| データ | 内容 |
|---|---|
| 直近メッセージ | 最大3件（設定で変更可能） |
| ルーム名 | 現在のチャットルーム名 |
| 返信意図 | 社員が入力したテキスト |

### 送信しないデータ

- Chatworkの全履歴
- メンバー一覧
- ファイル添付
- Chatworkの認証情報
- 他のタブの情報

### 個人情報マスク

送信前に以下を自動マスクします（ベストエフォート）。

- メールアドレス → `[EMAIL]`
- 電話番号 → `[PHONE]`
- クレジットカード番号風の数字列 → `[CARD]`

ただし**完全な保護は保証できません**（SECURITY.md参照）。

### Gemini のデータ取り扱い

- **Gemini API 有料プラン**: 送信データはモデル学習に使用されない
- **Gemini API 無料プラン**: 送信データが学習に使われる可能性あり

**業務データを扱う場合は有料プランの利用を推奨します。**
利用規約を確認の上、社内のデータポリシーに準拠してください。

## Q5. 100人に配布するときのベストプラクティス

### 配布方法

| 方法 | メリット | デメリット |
|---|---|---|
| **Chrome管理コンソール** | 自動インストール・自動更新 | Google Workspace が必要 |
| **社内サーバーからCRX配布** | インフラ不要 | 手動更新 |
| **zip配布 + マニュアル** | 最も簡単 | 更新管理が大変 |

### 推奨構成（100人規模）

```
1. config.js にデフォルトURL + APIキーを設定
2. GCP API Gateway でリファラー制限・IP制限を設定
3. Gemini API 有料プランを利用
4. Chrome管理コンソールで自動配布
5. APIキーは四半期ごとにローテーション
6. Cloud Audit Logs でアクセスを監視
```

### APIキーローテーション手順

1. GCP Console で新しいAPIキーを発行（旧キーも一定期間有効にする）
2. `config.js` の `DEFAULT_API_KEY` を新キーに更新
3. 拡張を再配布（Chrome管理コンソールなら自動）
4. 移行期間後、GCP Console で旧キーを無効化

## Q6. 拡張機能のソースコードは外部に公開されるの？

### 短い回答

**いいえ、インターネット上には公開されません。** 見れるのはインストールしたPC上だけです。

### 配布の仕組み

```
管理者がzipや管理コンソールで配布
    │
    ▼
社員AのPC → Chromeにインストール → そのPC内にファイルがコピーされる
社員BのPC → Chromeにインストール → そのPC内にファイルがコピーされる
```

- Chromeウェブストアには公開しない（社内配布のみ）
- 各社員のPCにローカルコピーされるだけ
- 社外の人がインターネット経由でソースを見ることはできない
- 社内のExcelマクロやバッチファイルを配るのと同じ感覚

### ただし「そのPCを使う人」には見える

```
chrome://extensions → 拡張の詳細 → ソースを表示
```

この操作でconfig.jsの中身（URL・APIキー）は読めます。
しかし**社員は正規ユーザーなので、見えて当然**です。

## Q7. APIキーも直書き（直貼り）で大丈夫？

### 短い回答

**Chrome拡張でAPIキーを完全に隠す方法はありません。** ただし、それでもAPIキー認証は有効です。

### 2つの設定方法

| 方法 | やり方 | 向いているケース |
|---|---|---|
| **config.js に埋め込み** | `DEFAULT_API_KEY = 'xxx'` と書いて配布 | 全員共通キーで簡単に運用したい場合 |
| **設定画面で各自入力** | 社員が設定画面の「APIキー」欄に入力 | 社員ごとに別キーを割り当てたい場合 |

### なぜ「見える」のに意味があるのか

**銀行のキャッシュカードの暗証番号と同じ考え方**です。

- 本人が暗証番号を知っている → 当然（正規ユーザーだから）
- 他人に暗証番号が渡った → 暗証番号を変更すれば無効化

APIキーも同様です。

| 状況 | 対応 |
|---|---|
| 社員がAPIキーを見れる | **問題なし**（正規ユーザー） |
| 退職者がAPIキーを知っている | **APIキーを変更**すれば即無効化 |
| PCが盗まれた | **APIキーを変更** + リファラー制限で不正利用を防止 |

### PCにインストールするアプリ全般の宿命

これはChrome拡張に限った話ではありません。

- Slackのデスクトップアプリ → 認証トークンはPC内にある
- Gitの設定 → 認証情報はPC内にある
- VPNクライアント → 接続情報はPC内にある

**PC上にあるものは、そのPCの利用者には見える。**
だからこそ「漏れた時にすぐ無効化できる仕組み（APIキー変更）」が重要です。

### 社内VPNとは

**会社のネットワーク内からしかアクセスできなくする仕組み**です。

```
【VPNなしの場合】
社員のPC ──(インターネット)──→ GCP API Gateway   ← OK
外部の人 ──(インターネット)──→ GCP API Gateway   ← APIキー+リファラー制限で拒否

【VPN + IP制限ありの場合】
社員のPC ──(社内VPN)──→ GCP API Gateway   ← OK
外部の人 ──(インターネット)──✕               ← IP制限でブロック
```

自宅から仕事するとき「VPN接続してください」と言われることがあれば、まさにそれです。
VPN + IP制限があれば、仮にURLとAPIキーが漏れても社外からはアクセスできません。

## Q8. GCPが落ちたらどうなる？

拡張機能は「AIが応答できません」とエラー表示するだけです。
Chatwork自体の動作には一切影響しません。
送信ボタンを自動で押す機能はないため、誤送信のリスクもありません。

GCPはGoogleが運用するクラウド基盤のため、一般的に稼働率 99.9% 以上が保証されています。

## Q9. GCPならチャットの機密情報は安全？

### 短い回答

**適切に構成すれば十分安全です。** ただし「完全に安全」は存在しません。

### GCPが安全と言える根拠

| 根拠 | 説明 |
|---|---|
| **GCP内部で完結** | データは Google Cloud の内部ネットワークのみを通過 |
| **ISMAP認証** | 日本政府のクラウドセキュリティ評価制度をクリア済み |
| **ISO 27001 / SOC 2** | 国際的なセキュリティ認証を取得済み |
| **Cloud Audit Logs** | 誰がいつ何をしたか自動記録。改ざん不可 |
| **通信暗号化** | HTTPS/TLS 1.3 で通信を暗号化 |

### Gemini API のデータ取り扱いについて

Gemini API の有料プランでは、送信データがモデル学習に使用されないことが
Google の利用規約で明記されています。業務データを扱う場合は有料プランを利用してください。

### それでも残るリスク

| リスク | 対策 |
|---|---|
| Google Cloud の内部不正 | → Google の契約・認証制度で保証。自前サーバーより信頼性が高い |
| 拡張機能からの送信内容の傍受 | → HTTPS/TLS 1.3 で暗号化。PIIマスクも実施 |
| 社員がプロンプトに機密情報を直接入力 | → 運用ルールで禁止（技術的に完全防止は不可能） |

## Q10. 100人が同時にAI下書きを使っても大丈夫？

### 短い回答

**はい、問題ありません。** GCPはサーバーレスで自動スケールします。

### 具体的な数字

| 項目 | 上限 |
|---|---|
| Gemini Flash API | デフォルト 1,000〜2,000 RPM |
| Application Integration | 数百〜数千の同時実行 |
| API Gateway | 月200万コールまで無料 |

100人が全員同時にボタンを押しても、実際にはミリ秒単位でリクエストが分散するため、
瞬間的な上限を超えることはほぼありません。

万が一上限に近づいても、Googleに申請すれば無料でquota（割り当て）を引き上げできます。

### レスポンス速度

| ステップ | 時間 |
|---|---|
| 拡張 → API Gateway | 50〜100ms |
| API Gateway → Application Integration | 50〜100ms |
| Application Integration → Gemini Flash | 100〜200ms |
| **Gemini Flash 生成** | **500ms〜2,000ms** |
| レスポンス返却 | 100〜200ms |
| **合計** | **約 0.8〜2.6秒** |

**3秒以内の目標は達成可能です。**
