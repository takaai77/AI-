# FAQ（よくある質問）

## Q1. config.js にWebhook URLを直書きして大丈夫？社内配布だから安全？

### 短い回答

**「社内配布だから安全」とは言えません。** ただし、正しく多層防御すればリスクは十分低くできます。

### なぜ「社内配布 = 安全」ではないのか

Chrome拡張のソースコードは**誰でも閲覧可能**です。

```
chrome://extensions → 拡張ID → ソースを表示 → config.js が丸見え
```

つまり社員であれば全員がURLとトークンを読めます。さらに以下のリスクがあります。

| リスク | 説明 |
|---|---|
| **退職者リスク** | 退職した社員がURLを知ったまま離職する |
| **端末紛失・盗難** | PCが盗まれればソースを閲覧される |
| **スクリーンショット** | DevToolsを開いた画面の共有で漏洩 |
| **マルウェア** | PC上のマルウェアが拡張ファイルを読み取る |
| **社内の悪意あるユーザー** | URLを知れば外部ツールからリクエスト可能 |

### ではどうすれば安全か？（多層防御）

**URLが漏れても被害を最小化する設計**が重要です。

#### 必須対策（これだけは必ずやる）

| # | 対策 | 効果 |
|---|---|---|
| 1 | **n8nにBearer Token認証を設定** | URLだけでは叩けなくなる（今回実装済み） |
| 2 | **n8nを社内VPN内に配置** | 社外ネットワークからはアクセス不可 |
| 3 | **HTTPS必須** | 通信内容の盗聴を防止 |

#### 推奨対策（100人規模なら検討すべき）

| # | 対策 | 効果 |
|---|---|---|
| 4 | **IP制限** | 社内ネットワーク以外からのアクセスをブロック |
| 5 | **レートリミット** | 不正な大量リクエストを防止 |
| 6 | **トークンのローテーション** | 定期的にトークンを変更し、漏洩の影響を限定 |
| 7 | **n8n側のアクセスログ監視** | 異常なリクエストパターンを検知 |

#### 理想的な構成（余裕があれば）

| # | 対策 | 効果 |
|---|---|---|
| 8 | **社内APIゲートウェイを挟む** | n8n URLを完全に隠蔽 |
| 9 | **ユーザー認証（SSO連携）** | 誰がリクエストしたか特定できる |
| 10 | **Chrome管理コンソールで配布** | インストール管理、自動更新が可能 |

### 現在の拡張の保護レイヤー

```
[社員のブラウザ]
    │
    │ ① Bearer Token認証（Authorization ヘッダー）
    │ ② HTTPS通信
    │
    ▼
[n8n Webhook]  ← ③ 社内VPN内に配置（推奨）
    │            ← ④ IP制限（推奨）
    │            ← ⑤ レートリミット（推奨）
    ▼
[Gemini API]   ← APIキーはn8n側のみで管理（拡張には非保持）
```

### 結論

- config.js にURLを書くこと自体は**実用上は許容範囲**
- ただし**URLだけでアクセスできる状態はNG**
- **Bearer Token + VPN/IP制限**の組み合わせが最低ライン
- 「URLが漏れた前提」で被害が起きない設計にすることが本質

## Q2. Bearer Tokenもconfig.jsに書いたら同じでは？

### 短い回答

**その通り、config.js のトークンも社員には見えます。** しかしそれでも意味があります。

### なぜそれでも認証が有効なのか

| 保護対象 | URL直書きのみ | URL + Token |
|---|---|---|
| 社外からの不正アクセス | URLが漏れたらアウト | URL+Token両方が漏れないと攻撃不可 |
| 退職者 | URLだけで叩ける | **トークンをローテーションすれば無効化** |
| URLのクローラー発見 | そのままアクセス可能 | 認証で弾かれる |
| ログ監視 | リクエスト元の区別が困難 | Tokenで正規リクエストか判別可能 |

**最大のメリットはトークンのローテーション（定期変更）です。**
URLは構造的に変えにくいですが、トークンは簡単に変更でき、
config.js を更新して再配布すれば全社員に一括反映できます。

### さらに強固にするには

個人別トークンを設定画面で入力させる運用も可能です。

```
config.js の DEFAULT_AUTH_TOKEN = '';  （空にする）
↓
各社員が設定画面で自分のトークンを入力
↓
n8n側で個人別トークンを検証
```

これにより「誰がリクエストしたか」を特定でき、
退職時にその人のトークンだけ無効化できます。

## Q3. Gemini APIキーが拡張に入っていないのはなぜ？

Chrome拡張のソースコードは `chrome://extensions` から**誰でも閲覧可能**です。
APIキーを埋め込むと以下の問題が発生します。

- APIキーが漏洩し、不正利用される
- 利用量の制御ができなくなる（高額請求リスク）
- キーのローテーションに全社員の再設定が必要

**対策**: Gemini APIキーはn8nサーバー側の環境変数でのみ管理する。
拡張機能はWebhook URLのみを保持し、APIキーには一切触れない。

## Q4. 社員のChatwork会話内容がAIに送られるのが心配

### 送信するデータ

| データ | 内容 |
|---|---|
| 直近メッセージ | 最大5件（設定で変更可能） |
| ルーム名 | 現在のチャットルーム名 |
| 返信意図 | 社員が入力したテキスト |

### 送信しないデータ

- Chatworkの全履歴
- メンバー一覧
- ファイル添付
- Chatworkの認証情報
- 他のタブの情報

### 個人情報マスク

送信前に以下を自動マスクします（ベストエフォート）。

- メールアドレス → `[EMAIL]`
- 電話番号 → `[PHONE]`
- クレジットカード番号風の数字列 → `[CARD]`

ただし**完全な保護は保証できません**（SECURITY.md参照）。

### Gemini のデータ取り扱い

- **無料版 Gemini API**: 送信データがモデル学習に使われる可能性あり
- **Vertex AI（有料）**: データ学習なし、エンタープライズ向け

**業務データを扱う場合は Vertex AI の利用を強く推奨します。**

## Q5. 100人に配布するときのベストプラクティス

### 配布方法

| 方法 | メリット | デメリット |
|---|---|---|
| **Chrome管理コンソール** | 自動インストール・自動更新 | Google Workspace が必要 |
| **社内サーバーからCRX配布** | インフラ不要 | 手動更新 |
| **zip配布 + マニュアル** | 最も簡単 | 更新管理が大変 |

### 推奨構成（100人規模）

```
1. config.js にデフォルトURL + トークンを設定
2. n8n は社内VPN内に配置
3. n8n に Header Auth (Bearer Token) を設定
4. Vertex AI を利用（データ学習なし）
5. Chrome管理コンソールで自動配布
6. トークンは四半期ごとにローテーション
7. n8n のアクセスログを監視
```

### トークンローテーション手順

1. n8n 側で新しいトークンを設定（旧トークンも一定期間有効にする）
2. `config.js` の `DEFAULT_AUTH_TOKEN` を新トークンに更新
3. 拡張を再配布（Chrome管理コンソールなら自動）
4. 移行期間後、n8n 側で旧トークンを無効化

## Q6. n8n が落ちたらどうなる？

拡張機能は「AIが応答できません」とエラー表示するだけです。
Chatwork自体の動作には一切影響しません。
送信ボタンを自動で押す機能はないため、誤送信のリスクもありません。
