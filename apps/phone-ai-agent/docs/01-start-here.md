# Start Here

この文書は、非エンジニアでも「このアプリは何でできているか」を部品単位で理解するための入口です。

## 1. このアプリを一言でいうと

「定期便の停止・変更を受け付ける会話オペレーター」を、AI と業務ロジックで分けて作ったものです。

重要なのは、AI が全部を決めているわけではないことです。  
安全に動かすために、役割を分けています。

## 2. 4つの層で考える

このアプリは、次の4層で見ると理解しやすいです。

### 層1. 入り口

ユーザーがどこから入るかです。

- 電話
  - Twilio 経由
- ブラウザ
  - マイク + 画面操作

ポイント:

- 入り口は複数あってよい
- でも中の業務ルールはなるべく共通にする

### 層2. 会話エンジン

実際に受け答えする AI です。

- OpenAI
- Gemini

ポイント:

- モデルは交換可能にする
- 交換しても業務ルールが壊れないようにする

### 層3. 業務ルール

「何を許可し、何を禁止し、何を確認するか」です。

例:

- 本人確認が終わるまで変更を反映しない
- 停止や変更は一度提案してから確認を取る
- 最後は `1 / 2` で確定か取消しを取る

ポイント:

- ここは AI の気分で変えてはいけない
- 業務ルールはコード側で守る

### 層4. データ

顧客や定期便の情報です。

例:

- 顧客 ID
- 商品名
- 次回配送日
- 配送間隔
- 数量
- 住所

ポイント:

- AI はデータを直接好き勝手に書き換えない
- まず提案を作り、確認後に反映する

## 3. なぜノード型シナリオが必要か

会話を完全に自由にすると、便利に見えても運用品質が落ちやすいです。

ノード型にすると次が明確になります。

- 今どの段階か
- 次に何をすべきか
- 失敗したらどこへ戻るか
- 人に渡す条件は何か

つまり、会話を「文章」ではなく「状態遷移」として扱えます。

## 4. このアプリで見るべき主要ファイル

- `src/server.ts`

- `src/agent/build-call-agent.ts`

- `src/scenario.ts`

- `src/services/call-session.ts`

## 5. このアプリから学べる設計の基本

### 基本1. 入口と本体を分ける

電話とブラウザは入口が違うだけです。  
本体の業務ロジックは共通にできます。

### 基本2. AI とルールを分ける

AI は会話を担当し、ルールはコードで強制します。

### 基本3. 実行前に確認点を置く

いきなり更新せず、提案 -> 確認 -> 実行の3段階にすることで事故を減らします。

### 基本4. 状態を明示する

「今は本人確認前か、提案済みか、確認待ちか」を明示すると、設計が強くなります。
